It correctly diagnoses the manual babysitting / staleness / backpressure problems (verified via the exact motivating patterns in bundled/skills/implement/SKILL.md:404-419, pr-babysit/SKILL.md:407-439 and 20-background-tasks.md), and the 1:1 Flume port is faithful (all cited symbols/lines in manager.go:170/246, claim.go:56/74/106/312/448, sweeps.go:72/160/284/515/842, runner.go:242/794/1282, pkg/types/{types.go:356,validation.go:33}, logger.go:364 verified by direct reads/greps). Approve after addressing the two major issues below; the rest is minor polish or suggestions. 2 major + 3 minor + 4 nits identified.

## Issue 1: Tech stack and runtime model mismatch for proposed core components
- **Severity**: major
- **Section**: Proposed Design (Core Components 1-4, pseudocode for cycle/Claim/Run, Architecture Diagram, Runner Pseudocode), PR Plan (PR1 "new `internal/fleet/{orchestrator.go...}` (or equiv in harness lang)"), Data Model, Key Decision 1
- **Description**: The design ports Flume's in-process Go Manager (ticker + wakeChan + goroutines + semaphore.Weighted + dedicated sweeper goroutine) and file layout almost verbatim into the harness ("FleetOrchestrator.Run(ctx)", "pool.Submit", "golang.org/x/sync/semaphore", "internal/fleet/orchestrator.go"). "The orchestrator is a small goroutine/loop equiv in TS/whatever harness lang" is acknowledged in Risks but not resolved. Harness runtime (observed via ~/.grok/bin/grok, sessions JSONL + meta.json, skills .md/.py, MCP/ACP, pager TUI, turn-based /loop/scheduler_create/monitor primitives, no Go sources under ~/.grok or harness references) is a conversational agent harness, not a long-running Go service mesh. A native heartbeat loop with wake signals inside the agent turn model risks conflicting with compaction, context management, and existing background task surfaces (already shared with subagents per 20-background-tasks.md:29). PR plan and pseudocode assume the port is straightforward.
- **Suggestion**: Add a dedicated "Runtime & Language Mapping" subsection early in Proposed Design. Explicitly map (or prototype) the cycle/sweeper/claimer to harness-native mechanisms (e.g. reuse scheduler_create + monitor + file watchers for "RunThrottled", existing task manager for pool state, no new goroutines). Update PR1 to include a 1-2 day spike: "Determine harness core implementation surface and prototype minimal FleetOrchestrator using only existing primitives." Adjust all pseudocode to be lang-agnostic or provide harness-equivalent examples. Revisit "small goroutine/loop" claim in Risks.
- **Status**: open

## Issue 3: PR Plan ordering, TUI integration, and test coverage leave gaps in incremental value and risk
- **Severity**: minor
- **Section**: PR Plan (all 6 PRs, "independently mergeable... cumulative value", "TUI shows fleet in Ctrl+T" in PR2, full enhancements in PR5, "e2e for 5-delegation batch" in PR6 only), Rollout Plan, Risks (TUI pane bloat, core complexity)
- **Description**: Plan is mostly well-ordered (state machine + durable first, then enqueue/tracking, then claimer/pool for real queuing/backpressure, sweeper for the motivating recovery, telemetry/TUI late, polish last). Flag + coexistence good. However: (a) TUI stubs mentioned in PR2 desc but real grouping/reasoning drawer/sweep action deferred to PR5 — risks dead UI code or doc/code drift in intermediates; (b) self-healing (stuck sweeps addressing "still running" post-compaction bug called out in motivation) lands in PR4; (c) no explicit harness e2e/integration test for the exact 5-contract replay scenario until PR6; (d) optimistic sizing ("1-3 days... experienced contributor") for changes touching tool registry, ACP, pager (open Q on ownership), and session load paths; (e) early PRs deliver "status" and "enqueue+basic spawn" but skills adoption (pr-babysit pattern update) only in PR6.
- **Suggestion**: Promote minimal TUI grouping (even read-only fleet list in existing Ctrl+T) to PR1 or PR2. Move a basic "stuck requeue + parent-comp" sweeper subset earlier (or into PR2 as manual fleet_sweep only). Add concrete harness e2e test task (replay the 5-delegation contract using new tools + assert no manual ID babysitting + durable recovery post-simulated compaction) to PR4 or PR5. Include "investigate pager vs core TUI ownership + minimal change spike" as explicit pre-PR1 or in PR1. Adjust PR titles/descriptions to be explicit about "stub" vs "full" UI. Add per-PR "risk if delayed" notes.
- **Status**: open

## Issue 4: Alternatives and Key Decisions strong but incomplete for harness context; one harness-native path underexplored
- **Severity**: minor
- **Section**: Alternatives Considered (1-4), Key Decisions (1-7), "These were chosen after weighing the 4 alternatives and Flume post-port lessons"
- **Description**: The 4 alternatives are fairly analyzed with correct rejections (pure skill would still pollute context + lack native TUI/heartbeat per our skill reads showing explicit manual arrays + get_ block loops; simple in-mem loses the durability that fixes the observed compaction bug; external queue overkill). Key Decisions (reuse spawn substrate, file durable+OCC, shadow Enforce day 1, multi-cadence sweeps, bridged reasoning + handoffs not transcripts, non-blocking enqueue, strict coexistence) are well-reasoned and cite Flume pain directly. However, a 5th harness-native alternative is only lightly touched in alt1 and not elevated: extend the *existing* shared background task / scheduler / monitor / todo_write surfaces (already unified for subagents + shells per 20-background-tasks.md and tools like scheduler_create) with fleet grouping, auto file-based sweeps (using /loop or monitor as heartbeat), and delegation records — achieving most reliability without a new "orchestrator" process/loop. This would better honor "minimal core change" for the harness.
- **Suggestion**: Add "Alternative 5: Harness-native fleet via extended scheduler + monitor + file-state orchestrator skill (no new core heartbeat)" with trade-offs (faster prototype, full coexistence, but less "first-class" than core; still needs durable records + state machine). Revisit Decision 7 and Risks "Added complexity in core harness runtime" in light of it. This makes the analysis more complete for a non-service system.
- **Status**: open

## Strengths
- **Exceptional concreteness and traceability**: Full component mapping table with exact Flume citations (file:func:line), Mermaid diagrams (architecture + sequence for the 5-batch case), pseudocode for cycle/claim/runner, exact tool signatures with before/after JS snippets, full JSON data model schemas, storage estimates (<100KB for 20), rollout with shadow/flag/rollback. An engineer *could* implement from this (modulo the issues above).
- **Faithful and verified Flume port**: Every major guard (decomposed_at + raw/struct belt-and-suspenders, OCC with seq/prim + EnforceOrLog at 100% writers, WIP/dedup (norm+semantic), adaptive multi-cadence sweeps, 2-pass parent comp, PM-block skip in resume, atomic combined decomp update + script, LogAgentReasoning non-blocking bridge with 409 retry, MAX_HIERARCHY_DEPTH, shadow default via env) was directly confirmed in the live Flume sources. No hallucinations.
- **Correct diagnosis of harness pain and preservation of fast path**: Manual ID tracking + polling loops, post-compaction staleness in get_ despite meta.json complete, lack of backpressure/claiming/sweeps, persona-via-prefix convention (not persona param), resume_from + worktree + capability + depth all preserved. Skills (implement 8+ parallel reviewers, pr-babysit explicit 8-cap + state file + block waits) match the "PM Decomposition Death Spiral" analogy exactly. Fast path (spawn_subagent) untouched.
- **Strong alternatives + decisions section**: 4 alternatives with honest trade-offs; 7 Key Decisions with rationale tied to Flume post-mortems and harness goals. Coexistence and "opt-in reliable path" are non-negotiable and correctly prioritized.
- **Good risk/rollout/observability coverage**: Severity-rated risks with mitigations, staged rollout with metrics gate, rich telemetry (thoughts[], FleetSnapshot, bridged reasoning, TUI grouping), debug tools (fleet_sweep, FLEET_DEBUG).
- **Format and review-friendliness**: Follows the exact structured notes format requested in the prompt (and used in this review); self-referential consistency (the design doc itself was produced under the review process it describes).
- **No scope creep**: Non-goals correctly exclude distributed queue, auto-merge, new personas, full TUI rewrite, sub-fleets initially.
